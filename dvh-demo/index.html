The problem with 100vh

On a phone, the browser toolbar takes space, then retracts as you scroll. The old vh unit measures the largest possible viewport, toolbars retracted. So a 100vh hero is taller than the visible screen on first load. The bottom of it, usually the button you most want tapped, sits under the toolbar.

The old fix was JavaScript: measure window.innerHeight on resize and set a custom property. It worked, but it was a workaround for something CSS should have known.

Three units for three toolbar states

UnitMeansUse it for
svhSmall viewport, toolbars fully visibleContent that must never be cut off
lvhLarge viewport, toolbars retractedImmersive backgrounds, same as old vh
dvhDynamic viewport, follows the toolbar as it movesMost full-height sections

The one-line fix

.hero {
  height: 100vh;   /* fallback for older browsers */
  height: 100dvh;  /* modern browsers use this */
}

Keep the vh line first. Browsers that do not know dvh ignore the second line and keep the fallback. Browsers that do know it override with the dynamic value.

Honest note: dvh resizes the element as the toolbar moves, which can cause visible reflow mid-scroll. If the section must never jump, svh is the stable choice: it always fits, even with the toolbar fully visible.

Support

Dynamic viewport units shipped in Chrome 108, Firefox 101, and Safari 15.4, so they work on iOS Safari, not just Chromium. Older browsers fall back to the vh line above.
